# Labelmaker profiling results — 2026-09-13

Nuke 17.0v3, Debian 12 container on an Intel N100 (4 cores, no GPU), Xvfb +
llvmpipe, Nuke's own DAG draw path driving the labels (`run_drawpath.sh`; see
`xvfb-draw-path-findings.md` for why the older `nuke.runIn` harness was
measuring the wrong thing). Raw outputs in `results/`.

**Caveat on absolute numbers.** This box throttles under sustained load: the
same step varies up to ~2.5× between runs (e.g. 5 007-node viewer connect,
Labelmaker: 0.82 s / 1.73 s / 2.13 s; stock: 0.35 / 0.39 / 0.52 s). Ratios
within a run are meaningful, absolute numbers are 2–3× pessimistic versus a
workstation. For workstation figures use the instrumented build's
`Edit > Labelmaker Profile > Dump Stats`.

## 1. When Nuke asks for a label (identical in stock and Labelmaker modes)

Unchanged from 801 to 10 002 nodes:

| event | label requests |
|---|---|
| zoom, pan, wheel, hover, select, click, node drag, move, select-all | **0** |
| knob edit, rename, disable, label knob, create, paste, undo | 1 per affected node |
| delete node, any wiring change (setInput, mask input, drag-wire, auto-rewire) | **0** |
| edit a `CTRL_` knob that other nodes reference by expression | **1** (the control only — dependents are NOT relabelled) |
| edit a cloned node | 2 (both clones) |
| open a Group in the DAG (`showDag`) | its innards (7–8); innards are not labelled at script open |
| script open, viewer connect (once per session per input), first frame change* | **every top-level node** |
| subsequent frame changes / scrub | frame-dependent nodes only: ~10% (996/10 002 stock, 1 102 with Labelmaker) |

\* the "every node" frame-change relabel happened once per session in the
full census; in the short re-runs (script open → frame change directly) only
the ~10% frame-dependent set was relabelled.

So label work is never redraw-driven; it is event-driven, and the expensive
events are the whole-script ones. Nuke does them in stock mode too.

## 4. Correctness issues found on the way

1. **Debounce cache drops trailing edits** (`create_autolabel`, commit
   94e313b + uncommitted): two edits 50 ms apart leave the first value on
   screen (knob `white`=3.2, label says `gain: 3.100`; same for `mix`). Nuke
   never re-requests after the window closes. And since Nuke never asks for
   the same label twice per redraw, the cache has no benefit — 0 hits in every
   census outside a synthetic 40 ms scrub and clone edits.
2. **Wiring changes never relabel.** Labelmaker's channels line reads the
   mask *input connection* (`node_mask_input_plugged`), so connecting or
   disconnecting a mask shows stale `M` state until the node is next
   invalidated. Stock only reads knobs and is immune.
3. **Expression-linked readouts go stale.** Editing `CTRL_00.gain` relabels
   only `CTRL_00`; every Grade whose `multiply` is `CTRL_00.gain*1` keeps its
   old colourised readout. Same for animated knobs across frame changes
   unless the node is in Nuke's frame-dependent set.

## 5. Recommendations, in order of payoff / effort

1. Remove the label cache + debounce timer (fixes #1; no measurable cost).
2. `node_has_mask`: `node.knob("maskChannelMask") is not None` instead of
   `"maskChannelMask" in node.knobs()` — ~15% of Labelmaker's per-label time,
   the single biggest Labelmaker-specific cost.
3. Skip `nuke.tcl("subst", s)` when `"[" not in s` (label knob and config
   `tcl_string`s) — ~10% at scale, zero behaviour change.
4. After 1–3 Labelmaker is ~1.5× stock per label; the remaining gap is the
   extra `nuke.value` reads for the readouts. Beyond that the pauses users
   see on 5–10k scripts (viewer connect, first frame change) are Nuke's
   whole-script relabel, which stock pays ~half of anyway.
5. #2/#3 (stale wiring/expression readouts) have no clean hook — Nuke has no
   input-changed or dependency-changed callback. Cheapest honest option is to
   document it; a `nuke.addUpdateUI` hook only fires for nodes with open
   panels.

# Part 2 — interactive profiling with real input (same day, later)

Everything above measured Python time per label. It missed what users feel,
for two reasons found afterwards: (1) the "GL events" rows were void — Nuke's
DAG ignores QTest-level events (a QTest drag leaves the node where it was);
real input now comes from **XTest** through the X server (`x_drag`, `x_wheel`,
`slider_drag`, `timeslider_drag` in `drawpath/menu.py`); (2) the cost that
matters is not the label build but what Nuke does *after* a label changes.
The metric is now **tick latency**: the main-loop stall per pointer event
during a 60 Hz gesture. Raw output: `results/abc_final*`, `results/xcensus_*`,
`results/diag_*`, `results/kc_*`, `results/r_*`.

## 6. What Nuke does around labels (measured, Nuke 17.0v3)

- **A changed label string costs Nuke an O(script) stall**: ~70 ms at 3 000
  nodes, ~200 ms at 10 000, regardless of which code produced it (stock label
  with a knob value appended shows the same stall), whether the node is
  visible, on-screen, or has a panel open. An unchanged string returned from
  the same build costs ~3 ms. (`results/diag_d3000_*.txt`, rows `D`/`P`.)
  Stock is immune during slider drags only because its text never contains
  knob values; Labelmaker's does, so every slider move changed the text.
- **Whole-script relabel passes** are scheduled by: a viewer input change,
  *any* real knob change on any node (a slider drag included), registering a
  Nuke callback, or a poke — and run at the **next frame change**, as one
  synchronous burst of every top-level node. A plain frame change relabels
  only frame-dependent nodes (~10 %). `nuke.frame()` inside the label makes
  the node frame-dependent.
- **Nothing programmatic re-requests one label** except a real value change
  on a non-UI knob. `dope_sheet`/`bookmark`/`cached`/`postage_stamp`/`label`
  change-and-revert in one callback → exactly one relabel, no undo entry (with
  `nuke.Undo.disable()`), no visible effect. `tile_color`, `note_font*`,
  `hide_input`, `icon`, `indicators`, `xpos` → nothing.
- **`knobChanged` fires per node per pointer move when dragging a
  selection**: 123 032 calls for one drag of 3 002 nodes (`xpos` × 40 moves),
  3 014 for a rubber-band select (`selected`). Unusable as an invalidation
  hook on big scripts. `opHashes()` is 0.5 µs but only live for viewed ops.
- Node dragging itself issues **no** label requests; its cost is Nuke's and
  identical across implementations (10k: 20–29 ms/tick for one node, ~500 ms
  for all nodes, all three implementations within noise, `results/r_d10000`).

## 8. Prototype (`LM_PROFILE_MODE=proto`, `drawpath/menu.py`) — measured

Design, in front of the unmodified `create_autolabel`, **no Nuke callbacks**:

1. **Burst detection.** Requests < 5 ms apart in one event-loop iteration
   are one pass. Past 8 requests, every node with a cached label is answered
   from the cache (6 µs). A whole-script pass therefore costs hits plus the
   frame-dependent rebuilds; a lone edit (1–2 requests) rebuilds as before.
   Bursts of 9–200 are treated as genuine multi-node edits: served from
   cache now, refreshed at idle.
2. **Never hand Nuke a changed string during interaction.** Each edit still
   rebuilds (0.3–1 ms, to know whether the text changed) but the previous
   text is returned; the node is marked stale.
3. **Idle refresh.** Once label traffic has been quiet for a window
   (≥ 400 ms, 5× the measured stall), one pass pokes `dope_sheet`
   (change-and-revert, no undo) on every stale node → one relabel each, the
   new text is released, one stall — after the user has stopped.
4. Frame-dependent nodes (indicators bit 1/2 or `[` in the label) are cached
   per frame; in a burst on a new frame they are served stale and refreshed
   at idle, so scrubbing/playback does no label work until it stops.

Same session, implementations interleaved per gesture (`results/abc_final2_*`):

| gesture | nodes | stock | Labelmaker | **prototype** |
|---|---|---|---|---|
| slider drag | 3 002 | 16–23 | 120–128 | **20–25** (1 poke, final value correct) |
| slider drag | 10 002 | 14–22 | 154–188 | **13–18** |
| scrub | 3 002 | 47 | 174 | **5.5** |
| scrub | 10 002 | 185 | 270 | **27** |
| whole-script pass, warm | 3 002 | 213 ms | 405 ms | **60 ms** |
| whole-script pass, warm | 10 002 | 703 ms | 1 529 ms | **251 ms** (10 044 hits + 1 111 frame-dep builds) |
| drag 1 / all nodes | 10 002 | 23 / 509 | 21 / 515 | 21–29 / 496–556 |

(3k numbers were taken while the box was throttled — compare across the row,
not between rows.) The first whole-script pass after script open is still a
cold build (every implementation pays it; Labelmaker 2× stock per label —
the `node.knobs()` and `tcl subst` fixes from §5 apply there).

## 9. Recommendations (supersede §5 items 1 and 4)

1. Replace the 100 ms debounce with the prototype's scheme: burst-served
   content cache + deferred text changes + idle refresh via `dope_sheet`
   poke. No `knobChanged`/`onDestroy` registration.
2. Keep §5 items 2–3 (`node.knob("maskChannelMask")`, skip `tcl subst`
   without `[`) for the cold pass.
3. Do not read `nuke.frame()` for nodes that are not already frame-dependent.
4. Staleness model to document: readouts settle ~0.4 s after the last
   edit/frame change; labels of expression-linked dependents and mask-wiring
   still only refresh when Nuke next asks (unchanged from today).

**Hooks (`onCreate`/`onDestroy`) cost nothing measurable.** G1/G2 ran the
paste-1000 / delete / undo / redo / create-200 cycle with the hooks removed
and registered, G3 with empty callbacks: every configuration is inside the
run-to-run noise (paste 24–37 s, delete 1.4–2.3 s, undo 0.7–2.8 s). The
apparent stock-vs-Labelmaker gap in the M block was ordering, see next.

**Session growth (harness artifact, not Labelmaker).** `nuke.delete()` per
node followed by one `undo()` + `redo()` leaves the pasted nodes in the
script (Z: 3 003 → 4 003 → 5 003 → 6 003 nodes, `cache entries` tracks it),
so later steps ran on a bigger script and `frame +1` requests grew 3 003 →
10 143. Stock shows the identical growth (Z1–Z3 stock: redo 1 000 → 2 000 →
3 000 requests, delete 0.6 → 1.5 → 2.7 s). Python-driven edits (`setInput`,
`setValue`) only get an undo entry inside an explicit `nuke.Undo()` group,
and `nuke.collapseToGroup` blocks on a modal (expression links leaving the
group) under Xvfb — both are harness lessons, not product findings.

**The one real regression: bulk edits of > 200 nodes were left stale.** A
tool setting a knob on 1 000 selected nodes relabels them in one burst that
is deferred to the draw, so it is the same size and shape as a whole-script
pass; the cache served the old strings and, past `LABEL_BURST_GENUINE_MAX`,
never refreshed them (216/1000 showed the new label, 89 kept the old one
after clearing). Fix: a whole-script pass is only ever started by a frame
change or a viewer-input change (§6), so `_track_burst` now records
`(nuke.frame(), viewer inputs)` at the first request of a burst and
`_close_burst` refreshes any large burst that had neither. Cost: one poke
pass after a bulk edit (settle 1.9–3.5 s at 3k on the N100 vs 0.1 s stock);
a legitimately huge pass with no frame/viewer change would cost one
unnecessary poke pass. Verified 1000/1000 and 0/1000 after the fix
(`results/edge_d3000_E_tail.txt`); unit tests cover both classifications.
Residual: a bulk edit at the same frame as a *simultaneous* frame change is
still classified as a pass (documented staleness model applies).

## 11. Spike: verify-at-idle instead of burst classification (2026-09-14)

Raw: `results/spike_verify_d3000.txt` (correctness, stock + on),
`results/spike_verify_d3000_ro.txt`, `results/spike_nostamps_d3000.txt`,
`results/spike_probe*_d3000.txt` (event-loop probes),
`results/spike_verify_d10000.txt`, `results/spike_priority_d10000.txt`.
Harness group `S` in `drawpath/menu.py`.

**Why.** §10's fix decided correctness by classifying a burst (size, then
"was there a frame/viewer change"); any trigger not in that list, or a bulk
edit coinciding with one, leaves labels stale for good. The spike removes
classification: every label answered from the cache during a burst is
re-composed in the background once traffic is quiet (`nuke.runIn(name, …)`
for node context, read-only — the indicators knob write in Foundry's
`set_indicators` now happens only on a real request), in 15 ms slices on a
0 ms timer that back off while label traffic continues; only labels whose
text differs are poked. Frame-dependent labels (keys/expressions/`[tcl]` at
the last build) are verified first and released as soon as that phase ends,
then the rest. `LABEL_BURST_GENUINE_MAX` and the frame/viewer heuristic are
gone.

**Correctness (3k and 10k, every case OK):** bulk label edit on 100 / 1000 /
all 2992 nodes; bulk + `nuke.frame()` in the same callback; bulk +
`connectViewer` in the same callback; bulk then delete 100 of them before
idle; bulk then rename 100; bulk inside an undo group, then undo; bulk on
nodes inside a Group (once the Group is displayed — Nuke never asks for
labels it does not draw); bulk then `set_enabled(False)`; bulk then
`scriptClear` (queue emptied by `onDestroy`, `scriptOpen` afterwards is a
normal cold pass). No `runIn` on dead nodes (`toNode` guard), no leftovers.

**Cost.** Per whole-script pass (after an edit + frame step, or a viewer
connect), background compute ≈ 0.4 s at 3k / 1.6 s at 10k on the N100
(≈ 0.15 / 0.7 s workstation), then one poke batch for the labels that
changed — after a frame step that is the ~10 % frame-dependent readouts,
the same set stock relabels synchronously. Foreground pass cost is
unchanged (80–160 ms vs 316 ms stock at 3k). Interaction unaffected: slider
drag started right after a pass 19 ms/tick at 10k (stock 14–22, pre-cache
Labelmaker 154–266), `busy_exits` shows the verifier yielding.

| | stock | verify-at-idle |
|---|---|---|
| pass, 3k, stamps off: settle | 0.47 s | 0.9–1.3 s (verify 2608 in 0.40 s, 28 slices, no gaps) |
| pass, 3k, stamps on: settle | 0.47 s | 2.5 s (same compute; ~65 ms gaps between slices) |
| pass, 10k, stamps on: first release / settle | 0.7–2.0 s frozen | 2.4 s / 13 s (verify 8648 in 1.6 s across 11.7 s) |
| bulk label 1000, 10k | settle 0.1 s | settle 0.9 s, 1000/1000 |

**The gaps are Nuke's, not ours.** Probes chaining 0 ms timers: 0.1 ms
round trip idle; `runIn` + full compose ×30 per tick 4.6 ms work / 4.9 ms
round trip. The ~65 ms (3k) / ~215 ms (10k) gaps only appear after a frame
change and vanish with `postage_stamp` off on every node: they are Nuke
re-rendering Read thumbnails in the same idle slots. Stock pays them too;
they only stretch verification's wall time.

**Verdict.** Correctness no longer depends on anything we inferred about
Nuke's triggers. The price is that after a pass the frame-dependent
readouts land ~1–2.5 s later (workstation: less) instead of inside a
0.5–2 s UI freeze, and a script that is edited-and-stepped continuously
keeps the verifier busy in the gaps (bounded: the queue is a set, ≤ node
count, and it never runs during traffic). Recommend adopting this shape.
Residuals unchanged from §9 item 4: labels Nuke never re-requests
(expression sources, mask wiring) still update when it next asks.

## 12. Review fixes and expanded edge cases (2026-09-15)

`s_d10000_fixed.txt` and `v_d3000.txt` are code SHA `da3b88f`;
`v_d10000.txt` and `v_d3000_deoverlap.txt` are `94fff94`
(`labelmaker.py` identical to `da3b88f` for the `S`/`V` cases — `94fff94`

**Why.** `CODEX-REVIEW-FINDINGS.md` raised six issues against the verify-at-
idle cache in `labelmaker.py`: (1) verification re-executes label-knob
Tcl/Python; (2) one compose exception abandons the verify queue; (3)
`_release_stale` clears `_stale` before poking, so a failed poke loses
unattempted labels; (4) `_poke_nodes` unconditionally toggles `nuke.Undo`,
clobbering a caller's own disable; (5) a real label request can leave an
orphan entry in `_verify_first`; (6) the supporting evidence was
qualitative but incomplete. Six commits landed fixes for (1) and (4):
`2a5215a`, `566db23`, `bead3a6`, `ca80f86`, `e7c6bf3`, `bcdc0a3` (the last
also closes the double-Tcl symptom case (a) measures); (2), (3) and (5)
were fixed earlier (`a3995c1`, `70f719f`, `44b13df`). §8 of
`REVIEW-BRIEF-2026-09-14.md` listed the areas the §11 spike never exercised
— label-knob Tcl/Python side effects, a failing compose or poke, Undo
state across a poke, the Dope Sheet panel, Viewer playback/input
switching, LiveGroups/Precomps/Groups with `onCreate` Tcl, expression
dependents, and de-overlap interplay. Group `V` in `drawpath/menu.py`
(cases (a)-(k)) is that missing coverage, run at 3k and 10k nodes; group
`S` (§11) is re-run unchanged on the fixed HEAD to confirm nothing
